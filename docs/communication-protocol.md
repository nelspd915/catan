# Game Communication Protocol

This document defines the boundary between the browser client and the game
server. It is a protocol contract, not a final wire schema.

## Boundary

The server owns game truth. The client owns presentation and input.

The client sends intent:

```text
roll dice
build road at edge X
offer trade to player Y
end turn
```

The server validates the intent, updates authoritative state, computes official
derived state, and sends each player an updated view.

```text
client command
  -> server validation
  -> authoritative state update
  -> player-specific view
  -> client render
```

The client must never be trusted to declare game outcomes.

## State Ownership

### Server Canonical State

Only the server mutates the real game state:

- Board setup and topology.
- Players, seats, turn order, turn, and phase.
- Roads, settlements, cities, robber, ports, and remaining pieces.
- Resource hands, development card hands, and deck order.
- Dice rolls and all other random outcomes.
- Trades, discards, robber choices, and pending required actions.

### Server Official Derived State

The server also owns derived facts that affect legality, scoring, or game flow:

- Winner and game-over state.
- Victory points.
- Longest Road.
- Largest Army.
- Legal actions for the current phase.
- Required actions for each player.

These facts may be sent to clients, but the client does not decide them.

### Client Local State

The client owns UI-only state:

- Hovered or selected board element.
- Open panels and selected cards.
- Animations, sounds, and layout choices.
- Pending command indicators.
- Non-authoritative visual previews.

Client-side calculations are allowed for UI hints, but the server remains the
authority.

## Transport

Use HTTP for lobby and setup operations:

- Create game.
- List games.
- Join game.
- Load saved game.
- Serve frontend assets.

Use WebSocket for live gameplay:

- Connect or resume session.
- Send player commands.
- Receive snapshots, updates, and command results.
- Handle reconnects and resync.

## Player-Specific View

The server should not send raw canonical state. It should send a view filtered
for the receiving player.

Each view should include:

- Public board state.
- Public player summaries.
- The receiving player's private cards and private prompts.
- Other players' public hidden-info summaries, such as card counts.
- Current turn, phase, and active player.
- Public official derived state.
- Actions currently available to the receiving player.
- Current game version.

The frontend should render from this view plus local UI state.

## Client Messages

Client messages express requests, not outcomes.

Required fields for game commands:

- Command id, generated by the client for idempotency.
- Game id.
- Expected game version.
- Command kind.
- Command parameters.

The server should derive player identity from the authenticated session or
socket, not from a trusted client field.

Common command kinds:

- Roll dice.
- Build road, settlement, or city.
- Buy or play development card.
- Move robber.
- Discard resources.
- Offer, accept, reject, or cancel trade.
- End turn.

## Server Messages

Server messages communicate authoritative results.

Common message kinds:

- Snapshot.
- Incremental update.
- Command accepted.
- Command rejected.
- Resync required.
- Game ended.
- Protocol error.

Server messages should include:

- Game id.
- Current authoritative version.
- Related command id when applicable.
- Stable error code for rejected commands.
- Snapshot or update data needed to make the client current.

## Sync Model

Start with a snapshot-first protocol.

After an accepted command, the server sends each connected player a fresh
player-specific snapshot for the new game version. This avoids requiring the
client to rebuild official state from event history.

Every authoritative state change increments the game version.

Rules:

- Snapshots replace the client's current game view.
- Rejected commands do not advance the version.
- Commands include the client's expected version.
- Stale commands are rejected or require resync.
- Repeated command ids return the original result instead of applying twice.
- Incremental updates can be added later, but snapshots remain the recovery
  path.

On reconnect, the client sends its last seen version. The server either sends
missed updates or a fresh snapshot.

## Hidden Information

Hidden information must be filtered on the server before sending any message.

Clients may see:

- Their own resource cards.
- Their own development cards.
- Public board state.
- Public scores, awards, and visible played cards.
- Other players' card counts when visible by rule.

Clients must not see:

- Other players' resource card identities.
- Other players' unplayed development card identities.
- Development deck order.
- Future dice results.
- Server-only random seeds or validation state.

Put this filtering in one player-view construction layer.

## Command Rejection

Rejections should use stable codes instead of human text parsing.

Useful codes:

- Not your turn.
- Wrong phase.
- Stale version.
- Invalid target.
- Missing resources.
- Piece unavailable.
- Trade unavailable.
- Required action pending.
- Game ended.
- Unauthorized.

If the client is stale, the rejection should include the current version and
either include or require a fresh snapshot.

## Working Contract

Frontend and backend can work independently once these contracts are stable:

- Player-specific snapshot shape.
- Command names and parameters.
- Server message categories.
- Version and reconnect behavior.
- Hidden-information filtering.
- Official derived state included in views.

The frontend can build against mocked snapshots. The backend can test commands,
snapshots, rejections, versions, and hidden-information filtering without the
real UI.
